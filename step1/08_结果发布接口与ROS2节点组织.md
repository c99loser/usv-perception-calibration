# 环节八：结果发布接口与 ROS2 节点组织

## 1. 环节定位

结果发布接口决定感知算法能否被比赛平台识别。即使第一阶段算法结果还不够准确，也应尽早建立与比赛要求一致的发布接口。这样可以避免后期算法完成后才发现消息类型、话题名称或坐标系不符合要求。

该环节的目标是搭建 perception_user.py 或 ROS2 节点框架，完成订阅、处理、发布的基础闭环。

## 2. 需要发布的话题

根据任务要求，感知模块应发布：

```text
/world/obstacles/bev_check
/world/obstacles/buoys_check
/world/obstacles/boats_check
/world/obstacles/pillars_check
/world/obstacles/blocks_check
/world/obstacles/lidar_check
```

其中障碍物位置应以船中心为原点，PoseArray 格式参考真值话题。

## 3. 节点输入

节点应订阅：

```text
7 路 LiDAR PointCloud2
6 路 Camera Image
可选 CameraInfo
可选调试真值话题，仅离线评估使用
```

注意正式算法不应依赖真值话题。

## 4. 节点输出

| 输出话题 | 建议消息类型 | 内容 |
|---|---|---|
| `/world/obstacles/buoys_check` | PoseArray | 浮球相对位置 |
| `/world/obstacles/boats_check` | PoseArray | 游动船只相对位置 |
| `/world/obstacles/pillars_check` | PoseArray | 立柱相对位置 |
| `/world/obstacles/blocks_check` | PoseArray | 浮块相对位置 |
| `/world/obstacles/lidar_check` | PointCloud2 | 融合或处理后的点云 |
| `/world/obstacles/bev_check` | Image 或模板指定类型 | BEV 鸟瞰图 |

## 5. ROS2 节点组织建议

第一阶段可采用单节点结构，便于调试：

```text
perception_user.py
├── 读取参数
├── 创建订阅器
├── 同步数据
├── 点云处理
├── 图像处理
├── 目标检测
├── BEV 生成
└── 发布结果
```

后续可拆分为多节点：

```text
lidar_preprocess_node
camera_preprocess_node
object_detection_node
bev_generation_node
result_publisher_node
```

## 6. 配置文件要求

建议将以下内容写入 YAML：

```text
传感器 topic 名称
传感器初始外参
船体尺寸
点云滤波参数
图像矫正参数
聚类参数
发布频率
调试开关
```

避免在代码中写死参数。

## 7. 时间同步策略

第一阶段可以使用近邻时间同步：

```text
以 LiDAR 时间戳为主
寻找最近的相机帧
时间差小于阈值则认为同步
```

建议初始阈值：

```text
LiDAR-Camera 同步阈值：0.1 s ~ 0.2 s
```

后续可使用 message_filters 或自定义缓存队列。

## 8. 发布频率建议

点云处理频率可根据算力设置：

```text
LiDAR 原始频率：约 10 Hz
Camera 原始频率：约 5 Hz
第一版感知输出：2 Hz ~ 5 Hz
```

如果算力不足，第一阶段可以离线处理每隔几帧的数据。

## 9. 验收标准

本环节完成后，应满足：

- 节点能正常启动。
- 能订阅所有必要传感器话题。
- 能发布所有比赛要求话题。
- 发布消息的 frame_id、时间戳、坐标含义清晰。
- 在 RViz 或命令行中能查看结果。
- 即使没有检测目标，也能发布空 PoseArray，保证接口稳定。

## 10. 风险与应对

| 风险 | 应对方法 |
|---|---|
| 消息类型与赛事要求不一致 | 以赛事模板和示例代码为准 |
| 算法耗时过长 | 降低处理频率，先离线验证 |
| 多路传感器同步困难 | 使用缓存队列和近邻时间匹配 |
| 发布坐标方向错误 | 在 RViz 和 BEV 中加入坐标轴检查 |
| 空结果导致下游异常 | 始终发布合法空消息 |
